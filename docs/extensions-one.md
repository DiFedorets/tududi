# Расширения One в tududi

Форк добавляет минимальные доверенные расширения при сборке. Произвольные пакеты и горячая загрузка не поддерживаются.

## Подключение

- Серверный реестр: `backend/extensions/index.js`. Маршруты регистрируются после общей аутентификации и проверки подписки для обоих префиксов API. Собственные маршруты дополнительно проверяют доступ к исходным объектам.
- MCP: тот же реестр подключается через `backend/modules/mcp/toolRegistry.js` для HTTP и stdio. Проверка прав выполняется в общем сервисе, не только в HTTP middleware.
- Интерфейс: `frontend/extensions/index.tsx` перечисляет id, версию, путь, название и лениво загружаемую страницу. App подключает маршруты. Поиск истории открывается через общий верхний поиск; отдельного пункта в SidebarBoards нет. Другим модулям потребуется подходящая точка входа.
- Новый модуль не должен создавать вторую копию задач. Его собственные данные требуют миграции и проверенного экспорта/импорта. Внутренние модули не изолированы от процесса приложения и базы.

## История и поиск

Страница `/extensions/history` и API `/api/v1/extensions/history/search?query=...`. Параметры `limit` (1–100) и `offset` задают страницы. Запрос — лексический поиск по любому значимому слову, кавычки сохраняют фразу. Нормализуются Unicode, регистр кириллицы и ё/е. Это не семантический поиск и не доказательство отсутствия темы при нулевой выдаче.

Полные тексты задач, заметок и комментариев читаются с текущими правами. Унаследованное название задачи не считается совпадением в тексте комментария. Источники возвращают UID, автора, даты записи, точные строки, найденные таймкоды и ссылки. Дата записи или импорта не выдаётся за дату встречи. Результат содержит `has_more`; агент должен запрашивать следующие страницы при необходимости.

Полный источник и доступные связанные материалы: `/extensions/history/source/:type/:uid`. Поддерживаются `task`, `note`, `comment`. Поиск связей использует отношения задач и явные ссылки на доступные источники. Штатные wiki-ссылки по названиям не переписываются автоматически в UID.

MCP-инструменты: `search_history` и `history_source`. Старый MCP-инструмент `search` сохраняет прежнюю семантику. Верхний поиск без фильтров и фокуса теперь использует history для задач, заметок и комментариев, сохраняя штатную навигацию по проектам, областям и меткам. При установленных фильтрах или фокусе остаётся штатная выборка. Enter и ссылка «Все источники и ответ ИИ» открывают полный поиск по всем доступным источникам. Совпадения подсвечиваются по терминам, возвращённым сервером; в полном источнике есть переходы между совпадениями.

ИИ запускается только по действию пользователя. `/extensions/history/answer` возвращает один JSON-ответ, `/extensions/history/answer/stream` — NDJSON-события `sources`, `delta`, `done` либо `error`. Фрагменты передаются через существующие настройки провайдера пользователя; ключ не передаётся клиенту. Контекст ограничен восемью источниками. Ответ не является исчерпывающим обзором архива; полные источники доступны отдельно. Есть замеры поиска, первого видимого текста и полного ответа. Это ответы на отдельные вопросы, без постоянной истории диалога и без автоматического изменения задач.

Первая версия читает доступный корпус при запросе. Отдельного поискового сервера, векторной БД и фоновой очереди нет. При росте корпуса измерить время/память и только затем вводить индекс. Доступ проверяется при каждом чтении; результаты модели нельзя сохранять в общий для всех пользователей кэш.

## Безопасное редактирование заметок

GET заметки возвращает `revision`. Для изменения `title`, `content` или `tags` передать `expected_revision`; без неё API отвечает 428. При устаревшей версии — 409. Текст, новая версия и теги записываются в одной транзакции. Однократные косметические операции остаются совместимыми с прежними клиентами.

MCP `update_note` требует `expected_revision` из `get_note`. Нельзя автоматически подставлять новую версию и повторять устаревшее содержимое: сначала перечитать, затем объединить изменения.

При конфликте браузер сохраняет черновик отдельно по пользователю и UID заметки; раздел «Черновики конфликтов» позволяет скачать текст или создать отдельную заметку. Это восстановление конфликтной правки в том же браузере, не общая история версий и не серверный backup.

## Резервирование

Штатный формат 2 дополнен `data.history` (версия 1 для прежних данных, версия 2 при наличии One): комментарии и ответы, реакции, отношения задач, события, дневные планы и ссылки на общие проекты. Восстановление выполняется после создания всех аккаунтов экземпляра и использует UID, не исходные числовые ID. В персональном импорте неизвестное исходное авторство комментария сохраняется как метаданные; отсутствующие внешние ссылки учитываются в `missing_references`.

Восстанавливать такой архив следует этой версией форка: оригинальный tududi может проигнорировать дополнительную историю. Старые архивы не содержат отсутствующие данные, и исправленный импорт их не восстанавливает из ничего. Полная холодная копия SQLite, uploads и конфигурации остаётся отдельным способом восстановления.

## Проверки

Целевые интеграционные сценарии находятся в `backend/tests/integration/one-foundation-history.test.js`. Они покрывают конфликт, отсутствие версии, атомарность тегов, кириллицу, права и отзыв доступа, записи сотрудника в проекте владельца, общую выдачу UI/MCP, изоляцию контекста модели, поток ответа, перенос истории и миграцию свежей схемы.

Тесты запускаются на отдельной БД. Для проверки данных действующего экземпляра использовать HTTP API или открывать SQLite строго read-only. Не запускать Sequelize под root против рабочей БД контейнера: создаваемые WAL/SHM могут получить неподходящего владельца.

## Ответы и план (20.10.2026)

Модуль `one` подключён тем же реестром. Человеческий вход — «Ответы и план» в боковом меню, `/extensions/one`. В карточке задачи есть панель плана и предупреждение о неотвеченных комментариях. Это данные существующей задачи, не второй задачник.

**Диалог.** Включение правил персональное (`POST /extensions/one/enable`). Новое сообщение через браузер считается человеческим, через MCP — агентским. Сервер не принимает роль из тела REST-запроса. У отдельной учебной учётки можно явно задать `one_actor=agent`; это метаданные авторства, не выдача прав. Права на задачи проверяются прежним механизмом.

Каждый новый человеческий комментарий ждёт ответа агента. Общий агентский ответ снимает предыдущие долги в той же задаче; ответ с `parent_comment_id` снимает только долг в соответствующей ветке. Агенту нужно ответить содержательно: механизм фиксирует наличие ответа, а не оценивает его качество. Если последнее сообщение агента содержит `?`, задача появляется в очереди человека. Человеческий ответ возвращает ход агенту. Автоматического запуска агента или отправки модели нет.

Отслеживаемые комментарии нельзя переписать или удалить обычным методом удаления комментария. Задачу с неотвеченным человеческим комментарием нельзя завершить, архивировать или отменить; защищены API, MCP, завершение повторения и прямая смена статуса в SQLite. Физическое удаление задачи — отдельная штатная операция, оно не превращено в архивирование. Очереди включают уже закрытые задачи с долгами.

В старом импорте распознаются только явные заголовки «АРХИВ … • owner/agent». Тексты и исходные авторы сохраняются; неопознанные комментарии показаны счётчиком, роли по догадке не назначаются. Исторические переносы неизвестны: при включении за исходную точку берётся последнее присутствие открытой задачи в дневном плане, счётчик начинается с нуля.

**Планирование.** `one_plans` хранит личный выбор: конкретный `planned` или `week` (понедельник), никогда оба. `due_date` остаётся дедлайном. Назначение дня создаёт/обновляет элемент штатного дневного плана; перенос удаляет старое присутствие из текущих и будущих дней, сохраняя прошлые дневные снимки. Изменение штатного дневного плана синхронизируется обратно. Кандидаты не предлагают дело, уже взятое на будущий день/неделю. Виды и календари, использующие дедлайн, продолжают показывать дедлайн.

`moves` растёт только при смене одного рабочего дня на другой. Первый выбор дня, повторное сохранение того же дня, выбор недели и снятие плана счётчик не увеличивают. Последний рабочий день сохраняется при снятии плана. Каждое настоящее изменение попадает в события задачи. Дата «сегодня» берётся из часового пояса профиля.

Защита от двух вкладок: план задачи требует `expected_revision`; штатный дневной план для включённого профиля — версию дня и общую `expected_one_revision`. Устаревший план получает 409, без версии — 428. Черновик не следует повторять с автоматически подставленной свежей версией. Несохранённый дневной вариант можно скачать; конфликт в форме задачи сохраняет выбранные значения до явного перечитывания.

**API и MCP.** GET `/extensions/one` — очереди и планы; `/counts` — значки; `/tasks/:uid` — план одной задачи; PUT `/tasks/:uid/plan` — изменение. Префиксы `/api` и `/api/v1` одинаковы. MCP: `one_overview`, `one_task_plan`, `one_schedule`, `one_reply`. Сначала читать версию, затем менять план. План всегда личный для пользователя MCP; гостевой агент не получает право менять личный план владельца. Старый штатный MCP `search` не заменён поиском истории.

**Хранение и перенос.** Поля `one_role`, `one_pending`, `one_answered_at` комментария и `one_workflow` (роль профиля, версия личного плана, строки планирования по UID) включены в штатный экспорт истории версии 2. Импорт восстанавливает роли, очереди, переносы и версии. Предыдущий форк отклоняет эту версию истории, а не молча теряет новые поля. Оригинальный upstream может игнорировать расширение, поэтому для полноценного переезда нужен этот форк или явный конвертер. Холодная копия SQLite + uploads + конфигурация сохраняет всё.

Модуль One в этой поставке поддерживает **SQLite**. На другом диалекте включение и импорт профиля One запрещены, поскольку там ещё нет эквивалента защитных триггеров. Откат миграции удаляет новые поля и не сохраняет их смысл: для возврата к старой версии использовать предрелизную холодную копию, а не запускать down на рабочей истории.

Проверки: `one-workflow.test.js` (19 сценариев, включая настоящий HTTP MCP, гонки, права, перенос и up/down/up миграции); штатные comments, daily-plan, MCP и прежняя история; интерфейс PlanningControl, TodayPage и PlanMyDay. Проверка на отдельной копии и восстановление описаны в отчёте лаборатории.
