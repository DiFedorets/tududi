# #11: исправления повторов и устаревшего дневного снимка

23.10.2026. Ветка `codex/issue11-planning-fixes`, основана на аудите `d2ebd73c` и коде пилота `42fe1532`. [Первоначальный аудит](issue11-planning-audit-20261023.md) сохраняется как история найденных проблем. В этой ветке исправлены обе причины, уточнён контракт счётчика и добавлены регрессии. На пилот изменения не переносились.

## Исправлено

### Повторения: один механизм даты и проекций

`completeOccurrence` и пропуск occurrence используют `nativePlanning.updateDate`. Штатная дата, OnePlan и актуальная позиция DailyPlan меняются через общую транзакционную проекцию. MCP `complete_task` пользуется тем же исправленным сервисом. REST при вычисленном сервером переходе к следующему повторению передаёт внутренний признак `automaticRecurrence`.

`planning.change` принимает внутреннюю настройку подсчёта. Для автоматического следующего occurrence moves не увеличивается; существующее накопленное значение не обнуляется. `last_planned` и ревизия следуют новой дате. Последующее ручное изменение дня снова добавляет ровно 1 по прежнему правилу. Клиентский параметр с именем `automaticRecurrence` не может отключить подсчёт: REST выставляет внутреннюю настройку из собственного результата расчёта повторения.

Проверенный пример: 05.01 → ручной перенос 06.01 (moves=1) → завершение повторения 07.01 (moves=1) → пропуск к 08.01 (moves=1) → ручной перенос 09.01 (moves=2). Во всех шагах штатный день и проекции согласованы. Завершение серии без следующего occurrence и настоящее повторное открытие сохраняют план и счётчик.

### Записи адаптера инвалидируют снимки пустых дней

Model hooks транзакционных instance-записей OnePlan теперь повышают `User.one_plan_revision` в той же транзакции. Это охватывает создание первого плана, изменение дня/недели/очистку, а также обновление ревизии/счётчика. Штатный `planning.change` использует bulk update и своё прежнее однократное повышение общей ревизии; двойного повышения нет.

Сценарий из аудита теперь заканчивается конфликтом: старый редактор прочитал несуществовавший 10.01, адаптер выбрал 09.01, затем сохранение старого списка 10.01 отклоняется. Новая дата 09.01 и moves=1 остаются. Исправление находится в backend tududi; рабочий адаптер One не редактировался.

## Изоляция и данные

Использована новая отдельная копия холодной резервной базы `before-clean-install-20261023-155032`, а не текущая база пилота. Все контейнеры одноразовые, `--network none`, без production volumes; фоновые сервисы отключены. SQL FK включены, принудительная пересборка/очистка схемы не применялась. Веб-стенд не запускался.

Применялся тот же неизменённый исходник адаптера, SHA-256 `70d70a83a63c11624737b6c816e4f66a4714e94fe44b5dc9460ec7ba39dde6a5`. Как и в аудите, только в его одноразовой копии подставлен искусственный владелец и путь зависимости для builder-контейнера. Процесс рабочего обмена, config, checkpoint и One-доска не запускались и не менялись. SHA-256 исходной холодной базы совпадает с исходным manifest. Копии базы, адаптера и частные логи не входят в Git.
