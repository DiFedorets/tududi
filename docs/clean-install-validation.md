# Исправление чистой установки SQLite

23.10.2026, v1.9.6. Ветка `codex/fix-clean-install`, база `5b1b9f7b`. Все операции выполнялись в одноразовых контейнерах с `--network none`, на пустых базах, копиях тестовых fixtures и отдельной копии существующей холодной резервной базы. База пилота, его контейнер и One не подключались и не перезапускались.

## Причина и исправление

При свежей установке `db-prepare` сначала создаёт таблицы/индексы текущих моделей. Затем штатный мигратор запускает историю миграций. Две новые миграции предполагали, что их объектов ещё нет:

- `20261022000002-create-task-note-links`: повторное создание `task_note_links_pair_type` и `task_note_links_note`.
- `20261023000002-note-discussion-fragments`: повторное добавление `notes.discussion_date` и `note_fragments_original_selection`.

Миграции теперь проверяют существующие объекты внутри своей транзакции. Индекс с тем же именем принимается только при совпадении порядка колонок и уникальности; частичный SQLite-индекс не считается полноценным ограничением. Несовместимость останавливает миграцию с понятной ошибкой. Ошибки SQL не подавляются, журнал миграций не заполняется вручную и цепочка не пропускается.

Исправлены исторические миграции, новые миграции не добавлены. Поэтому на уже обновлённой базе с 172 записями изменения схемы не требуются. Никакие пользовательские записи для этого исправления преобразовывать не нужно.

## Проверки

Чистая установка проверена двумя путями: production `db-prepare` → `sequelize-cli db:migrate` и `db-prepare` → standalone `db-migrate.js`. Обе завершают все 172 миграции. Проверены создание пользователя, создание задачи и изменение даты через авторизованный API, повторный запуск без изменений схемы, наличие индексов/триггеров, `integrity_check=ok`, пустой `foreign_key_check`.

Добавлен `backend/tests/upgrade/fresh-sqlite-install.test.js`: 6 тестов успешно, включая повторное применение точного индекса и отказ при несовместимом/частичном индексе.

Итог полного `jest.upgrade.config.js`: **5 наборов, 106/106 тестов успешно** (214 секунд). Включены clean install, legacy upgrade, schema parity, migration history и SQLite foreign keys. ESLint изменённых JS-файлов и `git diff --check` прошли.

На копии существующей холодной резервной базы (`before-upcoming-width-20261023-144914`) выполнены два production bootstrap и standalone мигратор. Все 172 миграции уже были отмечены: это проверка безопасного повторного старта текущей базы, а не применения отсутствующих миграций. Сравнение хешей содержимого **всех таблиц**, включая планы, счётчики, комментарии и связи, подтвердило полное совпадение до/после. SQL-схема не изменилась, integrity — ok, FK-ошибок — 0. Исходный файл резервной базы проверен по SHA-256 до/после и не изменился. Копия и частные результаты хранятся вне Git.

Реальное применение ещё не выполненных миграций проверялось отдельно на копиях семи обезличенных legacy-баз: v1.2.4, v1.3.0, v1.3.1, v1.4.0, v1.4.2, v1.5.0, v1.6.0-rc.1. Набор проверяет сохранение количества строк, полный журнал миграций, повторный запуск, вход, чтение списков/метрик и запись через API. Первоначально 7 проверок падали на устаревшем предположении теста, что каждая таблица обязана иметь ORM-модель: журнал `task_context_history` создаётся миграцией. Проверка уточнена конкретным разрешением этой таблицы с проверкой её колонок и FK; произвольные дополнительные таблицы по-прежнему запрещены.

Регрессионные интеграционные проверки: **5 наборов, 66 тестов успешно** — `native-planning`, `one-workflow`, `strict-project-context`, `task-note-links`, `note-fragments`. Живой обмен с One не запускался.

## Воспроизведение

Только в изолированном окружении с зависимостями проекта и без production volumes:

```sh
cd backend
npx jest --config jest.upgrade.config.js --runInBand
NODE_ENV=test npx jest --runInBand tests/integration/native-planning.test.js tests/integration/one-workflow.test.js tests/integration/strict-project-context.test.js tests/integration/task-note-links.test.js tests/integration/note-fragments.test.js
```

Проверялся SQLite. PostgreSQL не запускался. Известные ранее разрешённые расхождения schema parity остаются в `tests/upgrade/known-schema-drift.json`; эта правка не расширяет allowlist. Переноса на пилот в этой задаче нет.
