# #3 — восстановление ограничений SQLite на отдельной копии

Проверено 22.10.2026. Ветка `codex/sqlite-foreign-key-repair`, база ветки `b834eee4` (код после #1). Пилот, его контейнер, конфигурация и рабочая синхронизация One не изменялись.

## Результат

На копии восстановлены 18 потерянных внешних ключей в семи таблицах. Число объявленных связей выросло с 81 до 99; все 99 ссылок текущих моделей существуют в SQL. Висячих ссылок нет, `integrity_check = ok`, `foreign_key_check` пуст.

По каждой исходной таблице сравнивались все строки и все поля, а не только количество. Единственное изменение данных — добавление имени новой миграции в `SequelizeMeta` (168 → 169). В частности, полностью совпали 291 задача, 42 заметки, 350 комментариев, 175 событий, 40 планов One, 4 дневных плана и 26 позиций дневных планов. Сохранены ID/UID, даты, ревизии и счётчики переносов. SQL-определения всех индексов, триггеров и представлений после восстановления совпали с исходными.

Это проверка отдельной копии согласованного снимка после развёртывания #1 от 22.10.2026, а не чтение текущей живой базы. Перед внедрением потребуется повторить аудит на свежей согласованной копии. Локальные базы, тексты записей, ключи и файлы пользователей в Git не добавляются.

## Изменения

- `utils/sqlite-rebuild.js`: пересоздание таблиц на одном выделенном соединении и в одной транзакции; переключение FK до начала транзакции; сохранение исходных SQL-определений, индексов, триггеров, представлений и AUTOINCREMENT. Общие триггеры и представления пересоздаются после восстановления всех таблиц. При любой ошибке изменения всей группы откатываются; флаг FK восстанавливается.
- `utils/migration-utils.js`: SQLite-ветви `safeChangeColumn` и `safeRemoveColumn` используют новый механизм вместо пересоздания только по упрощённому описанию колонок. Неизменяемые определения сохраняются; зависимые объекты при несовместимом удалении колонки вызывают отказ с откатом, а не молча исчезают.
- `20261022000001-restore-sqlite-foreign-keys.js`: новая forward-миграция для существующих баз. Перед записью проверяет предполагаемые связи на висячие ссылки. Не исправляет данные автоматически. Список связей и действий закреплён в миграции, не выводится из будущих версий моделей. Повторный запуск безопасен. Также проверяется существующая связь владельца календарного токена.
- Снимок схемы теперь содержит FK; schema parity обнаруживает отсутствующие связи. При сравнении учитывается нечувствительность SQLite к регистру имён: старое `Users` и новое `users` обозначают одну таблицу. Семь новых тестов проверяют сохранность объектов, правила связей, идемпотентность, отказ на плохих данных и откат.

Политика восстановленных связей соответствует текущим моделям: обязательные ссылки владельца — `CASCADE`; необязательные ссылки задач/заметок на контекст и родителей — `SET NULL`; ссылка на шаблон проекта — `NO ACTION`. Это не отменяет сервисную логику удаления: например, штатное удаление проекта по-прежнему удаляет его задачи и сохраняет заметки. Уже существующие правила остальных связей не переписывались. В частности, существующий `tags.user_id` сохраняет прежний `NO ACTION`, хотя модель указывает `CASCADE`; это отдельное различие политики, а не отсутствующая защита.

## Откат и последующее внедрение

Откат этой миграции — восстановление предшествующей резервной базы и прежнего кода. `db:migrate:undo` намеренно останавливается с понятной инструкцией: удалять ограничения вслепую нельзя, исходная схема разных установок отличается. Механизм восстановления проверен на отдельном файле; для проверки старого приложения использовалась ещё одна копия восстановленного файла.

При будущем согласованном внедрении:

1. Безопасно приостановить One после завершения текущей операции и остановить приложение.
2. Сохранить полную резервную копию базы с корректной обработкой WAL, uploads и конфигурации; зафиксировать прежний образ/commit. Проверить читаемость и SHA-256 резервной копии.
3. Повторить аудит актуальной копии; при плохих ссылках остановиться для разбора.
4. Применить новую миграцию, проверить число и определения FK, целостность, неизменность данных, планы, счётчики и API.
5. При неудаче остановить новый экземпляр, восстановить резервную базу и прежний образ, проверить API. До результата проверок One не возобновлять.
6. После успешных проверок возобновить One и проверить очередной проход обмена.

Этот порядок ещё не выполнялся на пилоте. Внешние файлы не меняются миграцией; стендовая проверка отката относится к базе и прежнему приложению. Проверенные правила пересоздания основаны на документации SQLite: https://www.sqlite.org/lang_altertable.html и https://www.sqlite.org/foreignkeys.html.
