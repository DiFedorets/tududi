## Принятые правила

- В проекте Task.area_id и Task.goal_id обязаны совпадать с Project.area_id и Project.goal_id, включая NULL. Самостоятельного переопределения у проектной задачи нет.
- Создание/перенос в проект принимает контекст проекта; попытка записать иные прямые значения не создаёт исключение из иерархии: в ответе API возвращается фактически сохранённый контекст проекта.
- Изменение области/цели проекта синхронно обновляет его задачи в той же операции БД. Правило действует для ORM, bulk и прямого SQL адаптера.
- Без проекта поля задаются напрямую. При снятии с проекта последние значения сохраняются как прямой контекст, после чего доступны для редактирования. Более ранний контекст до помещения в проект автоматически не восстанавливается; его прежние значения сохранены в журнале.
- В карточке проектной задачи область и цель показываются вместе с пояснением «заданы проектом», без редакторов. В форме задачи выбранный проект также исключает прямое назначение области.
- Область в списках и поиске определяется проектом; прямое поле учитывается только для задач без проекта. Персональное размещение общего проекта в области остаётся персональным и не меняет канонический проект владельца. Числовой area_id теперь использует те же правила области, что area_uid.
- Цель проектной задачи зеркалит цель проекта, поэтому задача также появляется в списке задач этой цели. Внутренняя структура самого проекта (его область и цель) в этой работе не перепроектировалась.

## Реализация и сохранность

Миграция `20261023000001-strict-task-project-context.js` добавляет task_context_history и правила БД. Перед первоначальным приведением контекста сохраняются прежние project_id/area_id/goal_id каждой меняемой задачи. При последующих автоматических изменениях прежние значения также сохраняются. История не содержит копий текстов задач и не выдаётся через публичный API.

На SQLite ограничения реализованы триггерами на вставку/изменение контекста задачи и изменение проекта. Изменения контекста не трогают даты, updated_at, UID, статусы, тексты, планы, переносы и связи. ORM после сохранения читает значения, фактически установленные БД. Миграция также содержит PostgreSQL-ветку; текущие проверки и стенд выполнялись только на SQLite, PostgreSQL в рантайме не проверялся.

Перед подготовкой снята холодная копия только тестового стенда #4: `source/tmp/issue5-hierarchy-checks/before-hierarchy.sqlite3`, отдельные db/uploads/env для нового экземпляра. Рабочие данные пилота не читались и не копировались в рамках этой работы.

В исходной копии противоречий не было: миграция не изменила ни одной существующей строки задач. Все прежние пользовательские таблицы, планы, счётчики, заметки и связи совпали; добавились история/триггеры и запись миграции. Несогласованных задач с проектом — 0, integrity_check=ok, FK-нарушений — 0.

Отдельно на одноразовом файле создано расхождение между контекстом проекта и его задач. Миграция привела 22 задачи к проекту; прежние поля каждой изменённой задачи найдены в истории. Все остальные поля задач и остальные пользовательские таблицы совпали с исходным тестовым файлом. Этот искусственный пример не переносился в показываемую базу.

Откат интерфейса для просмотра — сохранённый прежний стенд. Для возврата данных после пользовательских изменений сначала нужна полная копия текущего состояния. Down миграции снимает триггеры и удаляет журнал, но не возвращает автоматически старые контексты: старое состояние сохраняется в холодной копии, а выборочное восстановление возможно по журналу до его удаления. На пилоте миграция не запускалась.
